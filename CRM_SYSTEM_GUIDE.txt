1. WHAT IT IS AND WHY IT EXISTS
================================================================================

The AS Brokers CRM is a bespoke staff-facing pipeline and client-management
system — the "precision engine" for advisors to run leads, correspondence,
tasks, and funnel submissions without spreadsheet drudgery.

It lives at:

  /crm

It pairs with a client-facing portal at:

  /portal

VISION (Rolls-Royce Wealth Concierge)
--------------------------------------
  - Eliminate manual pipeline tracking (Kanban with persisted status)
  - Unified correspondence thread per lead (WhatsApp, email, portal — WhatsApp live)
  - Staff-scoped access (admin sees all; staff sees assigned leads only)
  - Compliance-first: audit trail via correspondence table, no mock CRM at runtime
  - Future: AI briefs, HubSpot bi-sync, Everest API, executive dashboard

WHAT IT IS NOT (yet)
--------------------
  - Not a fully RLS-enforced Supabase-native app — access control is in server actions
  - Not connected to contact form → auto lead creation (Resend/HubSpot only today)
  - Portal still uses mock wealth data (lib/mock-portal.ts)
  - No separate clients table — "clients" = won leads in crm_leads
  - lib/mock-crm.ts was deleted; all CRM UI reads real DB when DATABASE_URL is set

3. AUTHENTICATION AND ROLES
================================================================================

METHOD: Supabase Auth magic links (email OTP)
---------------------------------------------
  1. User enters email on /login
  2. signInWithOtp sends magic link
  3. User clicks link → /auth/callback?code=...&next=...
  4. Session cookies set via @supabase/ssr
  5. Redirect by role

ROLES (stored in user.app_metadata.role, lowercased)
----------------------------------------------------
  admin   — Full CRM access (all leads, all tasks)
  staff   — Assigned leads only (assigned_advisor = user.id)
  client  — Blocked from /crm layout; redirected to /portal
  (other) — Blocked from CRM; portal allowed if logged in

REDIRECT LOGIC
--------------
  Logged-in admin/staff on /login  → /crm (or ?next= if /crm path)
  Logged-in client on /login       → /portal
  Unauthenticated on /crm or /portal → /login?next={pathname}

SESSION HELPERS: lib/crm/session.ts
  crmRoleFromUser()      → admin | staff | null
  canAccessCrmRole()     → admin or staff only
  staffDisplayName()     → user_metadata.full_name or email prefix

LEGACY (not used for CRM login)
-------------------------------
  lib/mock-auth.ts — mock-crm-role cookies; only cleared on logout

SUPABASE CLIENTS: lib/supabase/server.ts
  createServerSupabaseClient()  — anon key + cookies (for auth)
  getSupabaseService()          — service role (bypasses RLS; not primary CRM path)

4. DATABASE SCHEMA (Drizzle — source of truth)
================================================================================

All CRM runtime data uses Drizzle ORM via getDb() → direct Postgres (DATABASE_URL).
This bypasses Supabase RLS. Schema defined in lib/db/schema.ts.

⚠️ WARNING: Old Supabase migrations (supabase/migrations/20260308000000_crm_schema.sql)
use different table names (leads, clients, staff with TEXT ids). Runtime code uses
the Drizzle schema below ONLY. Apply via npm run db:push, not old SQL migrations.

TABLE: crm_leads
----------------
  id                  uuid PK
  client_id           uuid → auth.users (optional portal client link)
  source_funnel       varchar (e.g. whatsapp_inbound)
  service_category    varchar (maps to ServiceCategory in lib/crm/types.ts)
  lead_score          int default 0
  pipeline_status     varchar — new | contacted | qualified | proposal | won | lost
  assigned_advisor    uuid → auth.users (staff scope filter)
  raw_payload         jsonb — contact fields live here:
                        name, email, phone, intent, company, capitalHint,
                        estimatedCapital, funnelData
  created_at          timestamptz

  "Clients" in UI = rows where pipeline_status = "won" (no separate clients table).

TABLE: correspondence
---------------------
  Unified message thread per lead:
  id, lead_id → crm_leads (cascade delete)
  channel       — whatsapp | email | portal
  sender_type   — client | staff | system
  message_body  text
  external_message_id — unique (Meta wamid for dedup)
  staff_user_id → auth.users (outbound staff messages)
  created_at

TABLE: global_notes
-------------------
  Team scratchpad (/crm/notes):
  id, content, author_id → auth.users, created_at

TABLE: lead_reminders
---------------------
  Scheduled follow-ups:
  id, lead_id, title, due_date, is_completed, created_at

TABLE: crm_tasks
----------------
  Advisor tasks:
  id, lead_id (optional), assignee_id → auth.users
  title, status (open | completed), due_date, created_at

FUNNEL / LEAD MAGNET TABLES (separate from pipeline)
----------------------------------------------------
  business_risk_reviews
  legacy_checklist_leads
  healthy_retirement_assessments

  Each has admin page under /crm/* with CSV export actions.

OTHER TABLES IN SAME SCHEMA FILE (not CRM core)
-----------------------------------------------
  resources + embeddings     — RAG/pgvector for chat
  client_insight_posts       — Blog Studio (see BLOG_STUDIO_GUIDE.txt)
  studio_notebook_notes      — Blog Studio scratchpad

MAPPING LAYER
-------------
  lib/crm/map-lead.ts  — crm_leads row → CrmLead UI type (reads raw_payload)
  lib/crm/map-crm.ts   — correspondence, reminders, tasks, notes, clients
  lib/crm/types.ts     — KANBAN_COLUMNS, SERVICE_LABELS, TypeScript interfaces
  lib/crm/utils.ts     — currency, phone, conversion rate, advisor label

APPLY SCHEMA
------------
  npm run db:push    — scripts/db-push.ts → drizzle-kit push

  Requires DATABASE_URL in .env.local / Vercel.

  Without DATABASE_URL: all CRM reads return []; mutations return error
  "Database is not configured."

5. SERVER ACTIONS
================================================================================

FILE: app/actions/crm.ts
All exports require requireCrmUser() (Supabase session + admin/staff).

READ
----
  getLeads()                    All leads (admin) or assigned only (staff)
  getLeadById(id)               Single lead with access check
  getLeadDetails(id)            Lead + correspondence + reminders + tasks
  getGlobalNotes()              All team notes, newest first
  getTasks()                    All tasks (admin) or assignee = user (staff)
  getClients()                  Won leads, scoped
  getClientById(id)             Won lead only
  getRecentCorrespondence()     Scoped recent messages

WRITE
-----
  addGlobalNote(content)
  addReminder(leadId, title, dueDate)
  addTask(leadId, title, dueDate, assigneeId)
  updateLeadStatus(leadId, newStatus)   — Kanban persist
  completeTask(taskId)                  — exists but tasks UI is read-only today

ACCESS CONTROL
--------------
  assertLeadAccess() — staff denied if assigned_advisor !== user.id
  Returns null / forbidden() rather than leaking lead existence

FILE: app/actions/whatsapp.ts
  sendWhatsAppMessage(leadId, text)
    - Auth + lead access check
    - Read phone from raw_payload
    - Meta Graph API v19.0 outbound
    - Insert correspondence (sender_type: staff, staff_user_id)

7. LEAD 360 AND WHATSAPP
================================================================================

LEAD DETAIL: components/crm/LeadDetailView.tsx
  - Contact info from raw_payload
  - Correspondence thread (real DB)
  - WhatsApp reply with optimistic UI
  - Quick-reply templates
  - Schedule reminder

GATE: components/crm/LeadDetailGate.tsx
  - Staff blocked if lead not assigned to them

INBOUND WHATSAPP
----------------
Webhook: app/api/webhooks/whatsapp/route.ts

  GET  — Meta subscription challenge (WHATSAPP_VERIFY_TOKEN)
  POST — HMAC verify (META_APP_SECRET) → parse → Trigger.dev task

Worker: trigger/whatsapp.ts — task process-whatsapp-inbound
  1. Match phone via leadPhoneMatches() SQL on raw_payload.phone
  2. No lead → INSERT crm_leads (source_funnel: whatsapp_inbound, status: new)
  3. INSERT correspondence with onConflictDoNothing on external_message_id
  4. Retries: 5 attempts, exponential backoff

Phone helpers:
  lib/whatsapp/meta-webhook.ts  — signature verify, message extraction
  lib/whatsapp/phone.ts           — E.164 ZA normalization
  lib/whatsapp/lead-phone.ts      — SQL regexp match (0 → 27 prefix)

OUTBOUND WHATSAPP
-----------------
  LeadDetailView → sendWhatsAppMessage (app/actions/whatsapp.ts)
  Requires: WHATSAPP_PHONE_NUMBER_ID, WHATSAPP_ACCESS_TOKEN

TRIGGER.DEV
-----------
  trigger.config.ts — project TRIGGER_PROJECT_REF (default in repo)
  trigger/generatePdf.ts — contact form PDF (separate from CRM)
  Worker env needs DATABASE_URL for inbound WhatsApp task

12. SECURITY MODEL
================================================================================

CURRENT (app-layer)
-------------------
  middleware.ts       — login required for /crm and /portal
  crm/layout.tsx      — hard gate: admin/staff only
  server actions      — requireCrmUser(), assertLeadAccess(), staff scoping in SQL
  WhatsApp webhook    — HMAC signature verification
  CRM routes          — X-Robots-Tag: noindex

NOT YET IMPLEMENTED (planned Phase 2)
-------------------------------------
  Supabase RLS policies:
    admin → all rows
    staff → assigned leads only
    client  → own data only

  CRM uses direct Postgres (Drizzle) which bypasses RLS regardless.
  Portal has no role gate in layout — any logged-in user can access mock portal.

IMPLICATIONS
------------
  1. DATABASE_URL on server = full DB access (expected for Drizzle)
  2. Staff scoping enforced in TypeScript, not DB — bugs could over-fetch
  3. Client users see mock portal data, not real holdings (safe but not live)
  4. getSupabaseService() bypasses RLS but CRM path does not use it for CRUD
